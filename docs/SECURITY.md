# Доступ и защита данных

## Модель доверия

Server Deck управляет VPS через SSH. Хост панели хранит приватные ключи управляемых серверов, служебные токены, реестр и ключ восстановления резервных копий. Пользователь с административным доступом к этому хосту или панели может получить значительные права на управляемых VPS.

Используйте отдельный хост и собственные учётные данные, ограничивайте доступ к панели, обновляйте поддерживаемую ОС. Не выдавайте учётную запись панели человеку, которому нельзя доверить администрирование подключённых серверов. Панель не является системой разграничения прав для взаимно недоверяющих арендаторов.

## Сеть и вход

Серверная часть и служба авторизации слушают loopback. Публичный доступ проходит через HTTPS-шлюз Caddy с проверкой пользовательской сессии и отдельным внутренним реквизитом шлюза. Не публикуйте внутренние порты приложения, авторизации и маршрутизатора встроенных панелей наружу.

В режиме домена основной сертификат выпускает Certbot; продление должно оставаться включённым. Без домена используется собственный сертификат на публичном IPv4 и высоком порту. Браузер предупреждает о нём: перед первичной настройкой сравните SHA-256-отпечаток сертификата с выводом установщика через доверенное SSH-соединение. Не принимайте произвольный сертификат без проверки. PWA и встроенные панели на отдельных именах требуют доверенного HTTPS-домена; его можно подключить позднее.

Доверие встроенной панели и её сертификату устанавливается через уже проверенное SSH-соединение; это не разрешение игнорировать любые ошибки TLS.

Свежая установка не имеет готовой учётной записи. Одноразовый код первичной настройки действует один час, отображается установщиком один раз и хранится на сервере только как хеш. Владелец вводит код на `/login/` и создаёт свои логин и пароль; завершить создание может только один запрос. Этот путь не изменяет уже существующую учётную запись. Хранилище аккаунтов отделено от исходного кода: `/etc/caddy/server-deck-accounts.d/accounts` имеет ограниченные права.

Пароли панели хранятся как bcrypt-хеши. Сессионные cookies имеют Secure и HttpOnly; режим «Запомнить меня» продлевает сессию, а не сохраняет открытый пароль. Используйте уникальный длинный пароль и выходите из панели на чужом устройстве. Одноразовый код настройки защищайте как секрет: знание кода до создания владельца даёт возможность занять установку.

## SSH и Fail2ban

Для каждого сервера предпочтителен отдельный SSH-ключ. Сравнивайте отпечаток ключа хоста по доверенному каналу. Не отключайте проверку host key ради устранения ошибки подключения.

Изменение SSH-паролей, запрет парольного входа и изменение root-доступа не являются обязательной частью подключения VPS. Сначала проверяйте зависимости Amnezia и других рабочих приложений. Настройка Fail2ban предназначена для ограниченного jail; она не должна заменять все существующие правила или сбрасывать действующие блокировки. До применения сверяйте порт SSH, разрешённые адреса, пороги и показанный план.

Локальные операции смены пароля и домена используют ограниченные root-helper по SSH. Если действующая политика запрещает такой вход, установщик её не ослабляет: служебные функции потребуют ручной настройки или root/sudo-восстановления. Не включайте публичный парольный root-доступ ради этих операций.

## Проверки блокировок

При обращении к Cheburcheck внешнему сервису передаются публичный адрес цели и сетевые данные запроса. SSH-ключи и пароли для такой проверки не нужны. Результат описывает наблюдения используемых зондов и их алгоритмов.

Ошибка SSH может быть вызвана сетью, самим сервером, настройкой доступа, ключом или перегрузкой. Она не доказывает блокировку IP по ТСПУ. Проверка TCP/TLS не является сквозной проверкой UDP/AWG, а различие между сетями не устанавливает виновника без дополнительных свидетельств.

## Каталог и обновления

Ссылка на публичный проект GitHub или GitLab — внешний источник данных и потенциально недоверенного кода. Добавление проекта не даёт ему права автоматически запускать установщик. Для применения нужен поддерживаемый рецепт, проверка источника и явное подтверждение. Для неизвестного проекта привязка версии задаётся вручную; это не подтверждает содержимое установленного бинарника. Учитывайте привилегии root при оценке стороннего проекта.

Неизвестная установленная версия, ошибка GitHub API, prerelease или устаревший результат не означают «установлена последняя версия». Сопоставляйте тип компонента, ветку, опубликованный релиз и время проверки. Для ядра Linux используйте статус исправления поставщика вашей ОС; одно лишь большее число версии не доказывает устранение CVE.

Уведомление об исправлении не устанавливает обновление и не перезагружает сервер. Пакетное обновление ОС может перезапускать службы собственными скриптами пакетов. Резервная копия и подтверждение плана уменьшают риск, но не дают гарантии отсутствия перерыва связи.

## Что нельзя публиковать

В публичный Git добавляйте исходники, тесты, шаблоны и обезличенную документацию. Не добавляйте:

- реальный `servers.json`, пользовательские IP/домены и имена серверов;
- `.ssh`, приватные ключи, `known_hosts` и `authorized_keys`;
- пароли, Telegram-токены, API-токены панелей, конфигурацию шлюза и сессионные cookies;
- `control-data`, ключ восстановления, архивы копий, базы истории и журналы действий;
- рабочие TLS-приватные ключи, содержимое `/etc/letsencrypt`, `/var/lib/server-deck-auth` или конфигурацию учётных записей;
- снимки экрана и отчёты, содержащие действительные адреса, ссылки клиентов либо конфигурации VPN.

`.gitignore` — вспомогательная защита: он не удаляет уже добавленные файлы и не очищает историю Git. Проверяйте список подготовленных файлов и историю перед публикацией. При попадании секрета в Git сначала отзовите или замените его; удаление файла последующим коммитом не отзывает секрет.

## Копии и инциденты

Храните копии вне хоста панели и отдельно сохраняйте ключ восстановления. Проверка подписи и расшифрования архива не заменяет испытание восстановления на отдельном тестовом хосте.

Если потерян контроль над панелью, ограничьте её сетевой доступ через консоль провайдера, отзовите токены и замените SSH-ключи управляемых серверов с доверенного устройства. Не полагайтесь только на изменение пароля панели: украденные SSH-ключи могут продолжать работать независимо от неё.
